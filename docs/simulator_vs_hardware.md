# シミュレータと実機は別物: 実機QPUの「クセ」

このリポジトリの例（[例14〜19](workshop.md)を含む）は、**すべて古典コンピュータ上の量子シミュレータ**で
実行したものです。ノイズのない理想的な量子コンピュータの振る舞いを、古典コンピュータが計算で再現しています。

blueqat MCP からは実機QPU（OQC Toshiko Tokyo-1）にもジョブを投げられますが、実機はシミュレータと同じ感覚では
使えません。このページでは、blueqat MCP のツールで実際に取得した実機のデータと公開されている研究をもとに、
その「クセ」をまとめます。

> データは **2026-10-04 時点**のスナップショットです（`get_hardware_status` / `get_hardware_calibration` /
> `get_qpu_next_window` / `get_pricing` で取得）。実機の数値は日々のキャリブレーションで変わります。
> このページを書くにあたって、実機へのジョブ投入（`submit_hardware_job`）は行っていません。

## まとめ（先に結論）

| | シミュレータ（`run_circuit` / `run_qaoa` / `run_vqe`） | 実機（`submit_hardware_job`） |
|---|---|---|
| ノイズ | なし（理想的な量子コンピュータ） | ゲート・測定のたびに誤りが入る |
| 量子ビット同士のつながり | どの組み合わせでも直接ゲートをかけられる | 隣り合った決まった組だけ。それ以外は経由（SWAP）が必要 |
| いつ使えるか | いつでも、数秒で結果が返る | 稼働時間帯のみ。順番待ちあり |
| QAOA / VQE | 専用ツールで一発 | 専用ツールなし。回路を自分で組んで投げる |
| 費用 | 無料 | ジョブ単位の課金（取り消し・返金不可）、月の回数上限あり |
| 結果の再現性 | `seed` を固定すれば同じ結果 | 同じ回路でも日によって結果の質が変わる |

**ワークショップの例をそのまま実機に載せると、今回のような「全探索と一致した」きれいな結果は期待できません。**
以下、それぞれ具体的に見ていきます。

## クセ1: ノイズ — 回路が長くなるほど答えが崩れる

`get_hardware_calibration` で取得した OQC Toshiko Tokyo-1 の値です（キャリブレーション日時 2026-10-03 21:44）。

| 指標 | 中央値 | 範囲 | 意味 |
|---|---|---|---|
| 2量子ビットゲートの忠実度（fCX） | 0.9565 | 0.862〜0.985 | 2量子ビットゲート1回あたり、約4%の確率で誤りが入る |
| 読み出しの忠実度（fRO） | 0.8875 | 0.514〜0.961 | 測定1回あたり、約11%の確率で0と1を読み間違える |
| T1（エネルギー緩和時間） | 約56マイクロ秒 | — | 量子状態が壊れるまでの時間の目安。これより十分短い時間で計算を終える必要がある |

これが何を意味するか、ざっくり見積もってみます（**誤りが独立に起きると仮定した粗い概算です**）。

- **読み出しだけで半分近く崩れる**: 5量子ビットを測定して全部正しく読める確率は 0.8875^5 ≈ **55%**。
  6量子ビットなら約49%です。計算が完璧でも、結果の半分近くはどこかのビットが読み間違えられています。
- **2量子ビットゲートを重ねるほど崩れる**: [例16](../examples/16_store_location.md)（出店候補地）のQUBOは
  5変数の全ペアに2次項があり（10組）、`steps: 2` のQAOAでは2量子ビットゲートが少なくとも40回ほど必要です。
  0.9565^40 ≈ **17%** で、1回も誤りが入らずに終わる確率は2割を切ります（後述のSWAPを含めるとさらに下がります）。

シミュレータでは最適解が256回中9回出ましたが、実機ではこの差がノイズに埋もれる可能性が高い、ということです。
IBMの研究チームによる超伝導量子ビットでのQAOAの検証でも、ゲート忠実度・ゲート速度・必要なショット数の多さが、
古典ソルバーに勝つための大きな障害だと結論づけられています
（[Weidenfeller et al., Quantum 6, 870 (2022)](https://quantum-journal.org/papers/q-2022-12-07-870/)）。

## クセ2: つながりが限られている — 離れた量子ビット同士は直接つなげない

シミュレータでは、どの2つの量子ビットにも直接2量子ビットゲートをかけられます。実機ではそうはいきません。

`get_hardware_calibration` の `topology` によると、Toshiko Tokyo-1 の32量子ビットのつながりは32本だけで、

- 隣が **2つ**の量子ビット: 24個
- 隣が **3つ**: 4個
- 隣が **1つ**: 4個
- **三角形（3つが互いにつながった組）は1つもない**

という、細い鎖のような形をしています。

例14〜19のQUBOは、ほとんどが「全員が全員と関係する」形（例14・16は5変数の全10ペア）です。こうした問題を
この形の実機に載せるには、量子ビットの中身を隣へ隣へと入れ替える **SWAP** 操作を挟む必要があります。
SWAP 1回は2量子ビットゲート3回ぶんに相当するので、クセ1のノイズがさらに積み上がります。
`submit_hardware_job` のツール定義の説明文（[参考](#参考)）にも「既定ではプロバイダ側が配置とルーティングを行い、SWAPが挿入されうる」
「`preserve_layout` を使う場合、物理的につながっていない組を指定するとジョブは失敗する」と明記されています。

接続が疎なハードウェアではSWAPの挿入による回路の深さとノイズの増加がQAOAの性能を強く制限することは、
研究でも繰り返し指摘されています（例: [FrozenQubits, arXiv:2210.17037](https://arxiv.org/pdf/2210.17037)、
[A SWAP-free Framework for QAOA](https://www.alphaxiv.org/abs/2604.25058)）。

## クセ3: 量子ビットごとに「当たり外れ」がある

同じチップの中でも、量子ビットの品質はばらつきます。2026-10-03のキャリブレーションでは、

- 読み出し忠実度が **0.8未満**の量子ビットが32個中7個。最悪の量子ビット16は **0.514**（ほぼコイン投げ）
- 32本のつながりのうち、2量子ビットゲートの忠実度が測定できているのは **16本だけ**。残り16本は測定値が空（`null`）
- T1 の値が空になっている量子ビットが9個

でした。実機で良い結果を出すには、その日のキャリブレーションを見て **品質の良い量子ビットとつながりを選ぶ**
作業が必要です（`get_hardware_calibration` のツール定義の説明文（[参考](#参考)）にも、投入前に高忠実度の量子ビットを選ぶよう書かれています）。
この数値は日々変わるので、昨日うまくいった配置が今日も最善とは限りません。

## クセ4: いつでも使えるわけではない

| | 2026-10-04 時点の状態 |
|---|---|
| 今動いているか（`active_now`） | **停止中** |
| 次の稼働開始（`get_qpu_next_window`） | 2026-10-05 00:50 UTC（日本時間 09:50） |
| 順番待ちのジョブ（`tasks_in_queue`） | 2件 |

シミュレータは数秒で結果が返りますが、実機は**稼働時間帯にしか動かず、時間外に投げたジョブは次の稼働まで
待たされます**。ワークショップ当日、デモの時間に実機が動いているとは限りません。

## クセ5: QAOA・VQEの「専用ツール」が実機にはない

シミュレータでは `run_qaoa` にQUBOを渡すだけで、回路の組み立てもパラメータの最適化もサーバーがやってくれます。
実機に使えるのは `submit_hardware_job` だけで、これは**ゲートの並び（回路）を受け取って測定結果を返す**だけの
ツールです。実機でQAOAをやるには、

1. QUBOからQAOA回路（ゲートの並び）を自分で組み立てる
2. パラメータ（角度）を決める。シミュレータで最適化した値（`run_qaoa` が返す `optimized_params`）を流用するのが現実的
3. 実機の量子ビット配置・つながりを考えて投入する
4. 待つ（稼働時間・順番待ち）
5. 返ってきた測定結果から、目的関数の値が一番良いものを探す（ノイズで制約違反の答えも多く混ざる）

という手順を踏む必要があります。パラメータの最適化を実機で回そうとすると、1回の評価ごとにジョブ投入と
順番待ちが発生するので、さらに現実的ではなくなります。

## クセ6: お金と回数の制約

`get_pricing` によると、実機ジョブは **基本料金10 JPYC + 1ショット0.1 JPYC**（256ショットで35.6 JPYC）で、
**投入後のキャンセル・返金はできません**。free tier では実機ジョブは月10回まで、1ジョブ256ショットまでです
（2026-10-04 時点で課金ルートは `enabled: false`、つまりまだ課金は動いていません）。
シミュレータのように「seedを変えてもう一回」を気軽に繰り返せる環境ではありません。

## では、実機を触る意味はないのか

あります。ただし目的が違います。

- **「本物の量子コンピュータが、今どのくらいノイズを持っているか」を体感する**: ベル状態（[例1](../examples/01_bell_state.md)）の
  ように答えが分かっている小さな回路を実機で動かし、シミュレータの結果（00と11が半々）からどれだけずれるかを見る。
  これは実機でしか得られない学びです。
- **量子乱数（[例6](../examples/06_quantum_random_number_generator.md)）**: 物理的な予測不可能性に価値がある用途では、
  シミュレータ（古典の疑似乱数で再現したもの）ではなく実機を使う意味があります。

一方で、**「組合せ最適化の答えを実機で出して、古典より良い答えを得る」ことは、現時点の実機と問題規模では
期待しないほうがよい**、というのが正直なところです。

## ワークショップでの扱い（おすすめ）

- 例14〜19のデモはシミュレータで行い、「これはノイズのない理想的な量子コンピュータを古典で再現したもの」と
  最初に伝える
- 実機を見せたい場合は、最適化問題ではなく**ベル状態のような答えが分かっている小さな回路**を事前に実行しておき、
  シミュレータとのずれを見せる（当日のライブ実行は稼働時間・順番待ちの都合で避ける）
- 「実機はクセが強く、使いこなすには量子ビットの選び方・回路の組み方・ノイズ対策の専門知識が要る」ことを、
  「量子が不要なケース」とあわせて伝える
